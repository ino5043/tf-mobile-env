# Before: tf-mobile-env なしの開発プロセス

## 課題サマリー

tf-mobile-env を使わずに同等のフラッシュカード学習アプリを開発した場合に直面する典型的な課題。

---

## 1. アーキテクチャ設計

### 問題

- 設計指針がなく、開発者ごとにバラバラな構造
- Clean Architecture を採用しても、レイヤー間の依存ルールが守られない
- domain 層に infrastructure の依存が混入
- ファイル配置が場当たり的（`utils/` に何でも入れる）

### 典型的なコード

```dart
// ❌ すべてが1ファイルに混在
class StudyScreen extends StatefulWidget {
  @override
  _StudyScreenState createState() => _StudyScreenState();
}

class _StudyScreenState extends State<StudyScreen> {
  List<Map<String, dynamic>> cards = [];

  Future<void> loadCards() async {
    final box = await Hive.openBox('cards');
    setState(() {
      cards = box.values.toList().cast<Map<String, dynamic>>();
    });
  }

  void rateCard(int quality) {
    // SM-2 ロジックが UI に直書き
    var ef = cards[index]['ef'] ?? 2.5;
    ef = ef + (0.1 - (5 - quality) * (0.08 + (5 - quality) * 0.02));
    if (ef < 1.3) ef = 1.3;
    // ...setState で更新
  }
}
```

### 工数

- アーキテクチャ設計の調査・検討: **2-3日**
- チーム内での合意形成: **1日**
- ADR 作成のプラクティスがない → 後から「なぜこう設計したか」不明

---

## 2. 状態管理

### 問題

- `setState` が画面全体に散在
- 状態の予測が困難、デバッグに時間がかかる
- テスタビリティが低い（Widget と状態が密結合）
- 画面間での状態共有が場当たり的

### 工数

- 状態管理ライブラリの選定: **1-2日**（BLoC vs Riverpod vs Provider の比較）
- 学習コスト: **2-3日**
- 既存 setState コードからの移行: **3-5日**

---

## 3. テスト

### 問題

- テストカバレッジ **0%** が多数のプロジェクトの現実
- TDD のプラクティスがチームに浸透していない
- テストフィクスチャの設計パターンがない
- BLoC テストの書き方がわからない

### 典型的な結果

```
❌ テスト 0件
❌ CI でテスト実行なし
❌ リグレッションをデプロイ後に発見
```

### 工数

- テスト戦略の策定: **1日**
- テストフレームワーク選定・セットアップ: **0.5日**
- テスト作成（ゼロから学習しながら）: **5-7日**

---

## 4. オフライン対応

### 問題

- ネットワーク障害時にアプリがクラッシュ
- ローカルDB の選定で迷う（SQLite? SharedPreferences? Hive?）
- Cache First 戦略のパターンがない
- Hive の TypeAdapter 設計パターンがない

### 工数

- ローカルDB 選定: **1日**
- キャッシュ戦略の設計: **1-2日**
- 実装: **2-3日**

---

## 5. アクセシビリティ

### 問題

- Semantics ラベルが未設定（VoiceOver/TalkBack で操作不可）
- タッチターゲットが 48x48dp 未満
- フォントスケーリング非対応
- reduce motion 非対応

### 典型的な結果

```
❌ VoiceOver で「ボタン」としか読み上げられない
❌ 高齢者や視覚障害者が使用不可
❌ ストア審査で指摘される可能性
```

### 工数

- アクセシビリティガイドラインの調査: **1-2日**
- 既存UIへの Semantics 追加: **2-3日**
- テスト・検証: **1日**

---

## 6. CI/CD

### 問題

- 手動ビルド・手動テスト
- コードフォーマットの不統一
- ストア申請のチェックリストが不明確

### 工数

- CI/CD パイプライン構築: **2-3日**
- Flutter Web デプロイ設定: **1日**

---

## 合計工数見積（素の開発）

| フェーズ | 工数 |
|---------|------|
| アーキテクチャ設計 | 3-4日 |
| 状態管理の選定・学習 | 3-5日 |
| コア実装（ドメイン + データ + UI） | 7-10日 |
| テスト（ゼロから） | 5-7日 |
| オフライン対応 | 3-5日 |
| アクセシビリティ対応 | 3-5日 |
| CI/CD 構築 | 2-3日 |
| **合計** | **26-39日（5-8週間）** |

### 品質リスク

- テストカバレッジ: **0-20%**（時間不足で省略されがち）
- アクセシビリティ: **未対応**（後回しにされがち）
- ADR: **0件**（文化がない）
- コードレビュー: **一貫性なし**（レビュー基準が不明確）
